# Keep database storage native and make recovery portable

Status: Accepted. Local backup/restore implementation: issue #2; opt-in daily Mac orchestration:
issue #23; guarded removal/recreation: issue #5. See
[verification scope](../development.md#verification-and-adoption-status) and
[format/recovery guide](../backup-restore.md) for tested scope and limitations.

Portability means being able to deploy a fresh instance elsewhere and restore its complete reading state, not preserving a particular data location or VM. Use SQLite in a project-owned Podman named volume on the VM's native Linux filesystem, with explicit backup and restore commands exporting complete instance backups outside the VM and Git checkout. This avoids a separate database service and makes recovery independent of the VM's survival.

## Considered options

- A Mac-directory bind mount makes files visible and preserves them automatically when the VM is removed, but introduces a shared-filesystem boundary for SQLite locking and durability.
- A named volume avoids that sharing layer but is lost with the VM unless backed up externally; choose it together with guarded backup and recovery, not on its own.
- An OPML subscription export is useful for importing feed choices, but cannot recover articles, users, configuration, or reading state.

## Consequences

- An instance backup includes the entire required FreshRSS data and recovery metadata, including the application version and image identity/platform. Use a standard portable archive with integrity verification rather than making a VM image the recovery interface.
- Quiesce all application writers, including scheduled fetching, before copying data. Publish completed archives atomically; preserve previous good backups when export fails.
- Issue #2 replaces the initial shutdown deferral: normal shutdown creates and verifies a consistent external backup after writers stop and before the VM stops. The explicitly configured `RSS_BACKUP_DIR` must be private and outside Git; no host destination is chosen silently. Backup failure leaves writers stopped, the VM running, source data intact and prior backups untouched. An already-stopped VM is not restarted just to repeat shutdown. Issue #5 supplies a separate preview-first VM-removal command requiring a running accessible owned source and a fresh successful, independently verified external instance backup. Older archives and `no_data` never authorize deletion; unavailable sources are preserved for owner/provider recovery without a data-loss override.
- VM removal refuses additional volumes, foreign containers/images and any rootful resources, including stopped containers/volumes/images: one instance backup covers only the selected volume, not everything in a VM. Validate rootless/derived-root connection ownership, preserve foreign connections/defaults and refuse a project default among other connections. Remove captured jobs through their existing lifecycle before dismantling infrastructure. Bind explicit consent to a current inspection plan and independently verify the fresh archive before native nonforce machine removal; never global prune/reset.
- Preserve a private versioned removing/removed receipt, backup and durable maintenance on interrupted/partial removal. After abrupt death following native rm, only the exact owned receipt plus matching `stopping_vm` hold, absent exact resources, reverified archive and unchanged foreign connections permit completion. Otherwise inspect/reconcile, never delete records to override uncertainty. Successful setup retires only that removed generation's owner/selection/provenance/security/Serve/intent/recovery records into a private retired directory, preserves baseline/additions and backup locators/evidence, then creates fresh ownership for absent resources; never fabricate ownership or adopt a colliding name.
- Restore into a fresh, explicitly named volume without implicitly overwriting or activating an existing instance. Activation requires a separate explicit owned-volume selection with the application stopped. Incomplete imports remain unselected and cannot be selected. After VM removal, setup then restore **before any empty application start** (restore may start only the owned VM), select the new volume and start with the recorded compatible image; use a fresh name rather than the initial selected volume name even when absent, and verify the old original volume is absent. Verify restored application behavior, including subscriptions, article content, FreshRSS users, and reading state. Deterministic removal/recreation checks are not real disposable VM teardown/authenticated recovery evidence; that full path remains unrun.
- Restore a compatible recorded application version first, select an image appropriate to the destination architecture, and adjust host-specific settings such as the external URL. Neither an architecture-specific image digest nor a database downgrade is assumed portable.
- Backups contain credentials and private feed URLs. Keep them outside Git with restrictive permissions; these permissions are not encryption. Environment cleanup preserves external backups, and permanent data deletion is a distinct, explicitly confirmed operation. Automated permanent deletion targets only an explicit labelled unselected volume with zero mounts/no attachments, including stopped containers, uses nonforce native removal and makes no automatic backup. Archive deletion stays a manual exact-file double-review/confirmation procedure, never recursive directory cleanup or automatic pruning. Optional formula removal requires baseline/additions ownership, unchanged installed version, fresh recursive formula/cask reverse dependencies, no Podman machines/connections and both current-plan confirmation and per-candidate unused-elsewhere attestation; native dependent checks remain enabled. No automatic cache/directory/package sweep is justified by an installation ledger.
- Opt-in Mac daily orchestration reuses the same guarded archive boundary and explicit private destination, rather than adding an export/transfer engine. Daily attempt, verified publication and safe resumption are separate evidence. Any durable maintenance-marker presence plus one inherited nonblocking project lock prevents supervision from reopening writers after parent-process death; releasing the hold requires explicit owner/schema validation and idle-engine reconciliation, not guessing from elapsed time or PID reuse. Reconciliation never starts or changes intent, but retained running intent permits a later supervisor tick; explicit stop before reconciliation preserves stopped intent even if maintenance refuses shutdown. Backups never change persisted operator intent or resume intentional stopped intent. Normal stop retains the backup-orchestration wrapper and its evidence/maintenance handling.
- Do not automatically prune backups or articles. The initial production Mac slice adds daily scheduling and failure/freshness reporting, not automatic transfer, archive encryption/key management or database-engine changes. Actual Time Machine inclusion/copy retrieval/full-state recovery remain separate owner-coordinated evidence, not a consequence of local archive publication. Broader portable/Linux production operations remain deferred.

Implementation and verification: [backup and restore](https://github.com/brucepucci/rss-aggregator/issues/2) and [safe removal and recreation](https://github.com/brucepucci/rss-aggregator/issues/5).
