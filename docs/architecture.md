# Runtime architecture and safeguards

This is the implementation model for the Apple Silicon deployment. Use the [operator guide](../README.md), [configuration reference](configuration.md), [CLI reference](cli.md), [operations](operations.md), and [recovery guide](backup-restore.md) for practical steps.

## Deployment and storage

```text
ReadKit / browser → private tailnet HTTPS (optional Tailscale Serve)
                                      ↓
local browser → 127.0.0.1 : RSS_PORT → Caddy / FrankenPHP → upstream FreshRSS
                                                              ↓
                                              selected instance data / SQLite
```

FreshRSS runs as the normal macOS user. The installation's private state root separates pinned code, generated service configuration, instance data and lifecycle evidence. Only the selected instance serves requests and fetches feeds. SQLite stays on the native local filesystem, not in a synced path or against a separate database server. An owned directory is not a VM or a sandbox: the process runs with the user's permissions. The optional Tailscale proxy is not a database or identity provider.

[`cli.py`](../rss_aggregator/cli.py) adapts Click to callable [`Runtime.run`](../rss_aggregator/runtime.py). [`native_install.py`](../rss_aggregator/native_install.py) owns runtime artifact verification, [`native_service.py`](../rss_aggregator/native_service.py) the writer controller, and [`private_access.py`](../rss_aggregator/private_access.py) forwarding and API diagnostics. [`recovery.py`](../rss_aggregator/recovery.py) and [`archives.py`](../rss_aggregator/archives.py) handle instance provenance, snapshot, archive validation, and activation. [`supervision.py`](../rss_aggregator/supervision.py) and [`backup_schedule.py`](../rss_aggregator/backup_schedule.py) implement independent session policies through the same runtime guards.

## Pinned installation and security policy

The reviewed [native manifest](../config/native.json) binds the FreshRSS source revision and checksum to the official FrankenPHP macOS arm64 asset and its checksum, with exact PHP and Caddy version expectations. The installer verifies downloads before using them, refuses unsafe source archive entries and canonical-name collisions, probes the verified executable for versions and SQLite support, and records a digest of the private installed code tree. Setup revalidates a matching installation and refuses unowned paths or a different pin. A first-time root must be empty except for the recognized command lock; setup checks again with its own staging exempt immediately before claiming ownership. Status on unused state does not create a writer lease. Pre-install start, verify and backup refusals leave no running intent, writer lease or backup evidence that would prevent setup. This keeps it from claiming a parent that contains another installation. No shared installation or host PHP is used; metadata probes do not replace the effective web checks. Pin changes and their security review are explicit, not part of startup, migration or ordinary dependency updates.

## Startup security gate

The runtime checks native ownership, activation compatibility and the requested loopback port. For initialized data it configures SQLite FreshRSS with form authentication, anonymous access and anonymous refresh off, Google Reader-compatible API enabled, and upstream app updating disabled. A new uninitialized instance may expose the upstream installer on loopback only. Use [operations](operations.md) for the verification boundary before entering real credentials or forwarding to clients.

The runtime launches a detached Python controller for one generation. A dedicated child caretaker owns the pinned FrankenPHP web process and watches a pipe held only by that controller; closing the pipe, including on unexpected controller exit, closes the ordinary HTTP gate and triggers termination and reaping of that web process. The controller also launches scheduled upstream PHP fetching. The generated Caddy config binds IPv4 loopback, serves only FreshRSS's public tree, disables Caddy administration/config persistence/automatic HTTPS, and returns 503 to ordinary application requests until the controller acknowledges that generation's approval. The parent requires the same live generation, running scheduler and ordinary HTTP readiness before reporting success. Startup diagnostics use a generation-bound loopback host; the temporary probe and both approval markers are outside the public tree. The probe checks the effective web SAPI and PHP version, exact INI loading, no ambient INI scan, SQLite availability, that `session.upload_progress.enabled`, `expose_php` and `display_errors` are off, and the effective authentication settings for initialized data. The temporary probe is removed after every check. The runtime also checks loopback application response, scheduler and refusal of anonymous API requests before private publication. A different occupied port is tested before interrupting the current generation; a second bind check covers intervening changes but cannot reserve the port for the child. A repeated start rechecks current security before retaining a matching generation; failed checks and installer completion take the guarded restart path. Startup performs an immediate upstream fetch for initialized data. Missing startup templates are staged privately and published only when complete, without replacing existing files. Foreground PHP children use a private umask. Preparation, configuration and feed actualization run under detached caretakers with monotonic deadlines and a bounded drain on CLI exit. A caretaker and its PHP child keep writer exclusion, but not the command lock. A timeout reports a sanitized operation failure when the invoking CLI is still present.

A transient loopback disconnect counts as a failed probe; generation readiness retries within its existing startup window. The controller exits if it does not receive the current generation's security approval within the startup window. Once approved, it evaluates UTC 20-minute fetch slots (`*/20 * * * *`); missed slots are not replayed. Manual and periodic fetches share a fetch lease and still honor upstream TTL, cache and backoff. A scheduled-fetch caretaker keeps the 600-second monotonic deadline and reaps its PHP child even if the controller exits. A surviving controller records failure without giving up later eligible slots. Fetching from publishers is separate from client synchronization. The web and scheduled fetch children inherit the controller's writer lease. Stop requests address a specific service generation and drain owned children, not arbitrary PIDs from disk. A snapshot requires free writer and fetch leases and no conflicting controller lease. Inspection must not create a replacement lease to prove quiescence; missing or replaced managed leases are damaged evidence, not permission to capture.

## Session supervision and operator intent

A nonblocking per-state command lock serializes lifecycle, supervision, scheduling and recovery. The independent writer lease persists past the initiating CLI and through surviving writer children; a separate controller-only lease distinguishes a live controller from surviving orphaned writers. Status observes those leases without taking ownership of the service. Supervision compares the live port and access mode to its capture before accepting HTTP, scheduler and forwarding health. A disagreement vetoes recovery without spending an attempt. Per-state, per-role LaunchAgent identities and exact capture/ownership checks prevent a rehearsal job from adopting a production or legacy job. The ledger precedes publication; a private, fsynced complete plist is published without replacement so an interrupted staging write cannot leave a partial final definition. Read-only job inspections (launchctl queries and the captured Python import check) each time out after five seconds and do not inherit the command lock. Mutating launchctl calls have different ownership and outcome constraints. Removal checks the plist again after unloading before unlinking it. The normal GUI session is the service boundary; there is no pre-login startup or host power-policy change.

Only explicit start with a validated runtime sets running intent. Explicit stop revokes running intent even when a temporarily unavailable receipt prevents it from identifying owned resources. Backup quiescing does not set stopped intent. Supervision needs positive running intent and a valid captured job and stops retrying after a bounded budget (three recovery attempts with backoff). Status does not authorize a restart. Explicit start or healthy observation resets the budget. Reconciliation never changes intent: an explicit-stop hold or a later stop bound to the current hold requires durable stopped intent. Releasing a backup hold with no superseding stop can leave running intent in effect. See [captured settings](configuration.md#captured-mac-supervision-configuration) and [operations](operations.md).

## Private HTTPS and authentication

Tailscale Serve is an explicit opt-in, forwarding the node's owned HTTPS port 443 to the loopback backend. Preflight checks the connected node, HTTPS eligibility, effective access policy and route ownership. Repeat after preparation and startup fetch, just before opening the gated listener; recheck public routing before releasing the application gate. These are point-in-time checks, not a lock on independent Tailscale changes. Reject conflicting or changed 443 listeners and public Funnel routes reaching this backend rather than taking over or globally resetting them. If private preflight confirms public exposure of the active owned backend, request its shutdown without modifying the foreign route; unrelated conflicts don't stop a generation. Tailnet restrictions and TLS supplement, not replace, FreshRSS authentication. The authenticated diagnostic prompts for a separate per-user API password, rejects redirects, checks trusted HTTPS by default, and never returns tokens or response content. `--loopback` cannot verify TLS or actual ReadKit synchronization.

### Conditional forwarding ownership

Serve changes are conditional LocalAPI writes using the observed ETag; the application command lock cannot serialize independent Tailscale clients. The ownership ledger binds the exact route to this runtime. Before publishing, save pending intent; definitive refusal removes new authority before restoring the preceding local record. An ambiguous request retains evidence rather than triggering a global rollback. Before withdrawal, record relinquished authority; unknown withdrawal outcomes cannot justify adopting an identical recreated listener. Unrelated routes and Tailscale installation/configuration are preserved. See [private access](tailscale-readkit.md) for trusted-client and device checks.

### Post-start failure cleanup

Startup attempts to stop the owned writers and remove the temporary probe on failure after it enters the writer boundary. Startup cleanup conditionally withdraws only a route proved to have been published by that attempt, using its read-back snapshot. The writer shutdown path does not depend on successful conditional unpublication. Read-only Tailscale CLI queries and LocalAPI discovery time out after five seconds per invocation and do not inherit the command lock. A route mutation with uncertain outcome requires local inspection; a failed startup is not proof that Tailscale removed every route. Do not retarget another backend to an uncertain route or bypass an authentication/TLS gate to recover access.

## Daily backup orchestration

Daily backup is an independently opt-in normal-user-session job, not permission for periodic writer recovery. The job evaluates the latest elapsed eligible UTC slot under the command lock, even across midnight. Its daily journal retains the latest slot and retry budget per instance in the active registration, never reopening older slots after a clock correction. Invalid identity or attempt fields block replacement. A new registration can supersede valid old progress, not damaged evidence. Its own archived path and checksum are tied to a distinct registration and checked for availability independently of newer manual or shutdown archives. Explicit and scheduled backup share the same snapshot path; normal shutdown also verifies a complete backup where data exist and never resumes. The attempt, verified local archive and resumption are different facts; backup status reports them separately. Healthy daily publication targets roughly a day of data loss under normal operation, not guaranteed protection against losing the host.

Temporary backup quiescence first writes a durable maintenance marker that blocks recovery even if the orchestrating process dies. Under the command lock, explicit `stop` attempts to persist a hold, independent shutdown evidence and stopped intent. It uses the ownership receipt and writer leases to quiesce even if those writes fail, without relying on runtime layout, capture records or an available selection. The shutdown ledger records the affected instance and writer generation when known, including a matched generation still draining after its controller exits. A failed stop with an unreadable receipt in established state still leaves conservative failure evidence, but no authority to touch resources without the receipt. The ledger blocks green protection until a verified matching shutdown capture. Unidentified failures are not assigned to a later selection. Releasing a hold or taking a manual, daily or unrelated shutdown archive does not clear the failure.

Status validates each evidence record independently and probes readable access to regular files separately for the latest and scheduled archives, without rehashing their contents. The snapshot phase requires writer quiescence and a verified installed pin; unreadable capture state cannot authorize an archive. A live plan's instance must match the selection before readiness, foreground fetching or quiescence for backup; explicit stop can still quiesce identified writers. Backup may resume only the same previously running backend when intent permits, and only republishes forwarding it confirmed withdrawing. If an originally private backend resumes on loopback because its route is gone, its service plan retains the read-only Funnel check for subsequent backup resumptions, independently of private mode and publication authority.

Job ledger ownership is validated independently of layout health so damage can mark the scheduler unhealthy without hiding readable backup evidence. Reconcile only a recognized hold authenticated by the ownership receipt after confirming idle writers and no active owned forwarding. Layout verification belongs to capture and activation, not hold release; no time-based expiration or manual marker deletion. Recorded archive success may survive a failed resumption. Recent, registered daily protection is not evidence of Time Machine inclusion, independent retrieval or usable restored application state.

## Archive, recovery and retirement boundaries

A native v2 backup is a private ZIP (`manifest.json` and `data.tar`). The validator checks archive structure, exact compatibility identity (platform, FreshRSS version and source checksum, FrankenPHP version and executable checksum, PHP and Caddy versions), payload length/digest, and safe paths/types. Export charges the same cumulative path metadata budget as validation before staging each tar member; the budget limits path bookkeeping, not file payload size. Publication is atomic and non-overwriting after validation; previously verified archives survive a failed export. Checksums establish integrity, not the origin or independence of a copy. Only use trusted archives. The backup covers FreshRSS data, not the runtime installation, macOS jobs, or the rest of the host.

Backup paths are checked before creation against both configured and resolved ancestor ownership markers, including other native installs. Restore stages private files under a fresh instance name, then publishes without replacement or interrupting an active writer generation. Explicit selection while stopped is separate from both restore and startup; incomplete or incompatible instances cannot be activated. Default provisioning is recorded outside the instance directory so loss of previously provisioned data cannot be treated as a pristine install. A separate durable guard is written before the first explicit selection, so a missing selection cannot authorize fallback to `default`. While stopped, the operator can explicitly reselect the intended complete instance. The transitional v1 importer validates the reviewed legacy image and same FreshRSS release, maps the full payload to private native storage, and never accesses or changes the VM. It is not a fallback restore format or a supported reverse migration.

Upgrade and uninstall use a preview token bound to owned runtime state and the requested operation; they require stopped writers and retired job registrations and cannot delete instance data or backups. Upgrade is limited to PHP/web runtime changes for the same FreshRSS version, source digest and platform. Potential data writes during startup and serving belong to a durable per-instance writer generation. Fresh instance publication stages an explicit null generation; a missing generation record is not equivalent evidence for upgrade. With existing instances, apply independently revalidates the selected instance's recorded shutdown archive against the installed pin and requires it to cover the last writer generation before replacing the runtime. Unresolved shutdown evidence relevant to the selection and inconsistent generation records cannot authorize an older archive. Activation checks the source identity; archive restore still requires the exact full pin. A runtime change is not permission for a data-format conversion or a downgrade. Legacy VM retirement uses the [guarded historical procedure](https://github.com/brucepucci/rss-aggregator/blob/28664ab936f8872da6ff3ddca1c4b0a725dfb0ec/docs/operations.md#preview-and-remove-the-vm) only after the owner-assisted live and independent-copy gates. Nothing in native uninstall retires legacy resources.
